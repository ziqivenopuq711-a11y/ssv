Complete guide for participating in the SSV Bug Bounty program: submission process, severity classification, PoC requirements, and protocol architecture overview.

Getting Started with SSV Bug Bounty

This documentation provides everything you need to participate in the SSV Network Bug Bounty Program effectively. Whether you are a seasoned security researcher or discovering the program for the first time, this guide will walk you through the submission process, severity classification criteria, reward calculations, and best practices for responsible disclosure.

The SSV Network Bug Bounty Program is managed through the Immunefi platform — the leading Web3 bug bounty service. All submissions must be made through Immunefi. Direct disclosure to SSV Labs without going through Immunefi will not be eligible for rewards.

Quick Start: To submit a vulnerability report, create an Immunefi account, navigate to the SSV Network program page, and click "Submit Report." Ensure your submission includes a full proof of concept and follows the guidelines in this documentation.

How to Write a Quality Report

A high-quality bug report dramatically increases the likelihood of a fast triage and maximum reward. Every submission should contain all of the following components:

1. Vulnerability Summary

A concise one-paragraph description of the vulnerability. Include the affected contract, function name, and the nature of the bug (e.g., reentrancy, access control bypass, integer overflow). Avoid jargon that is not standard in the security community.

2. Impact Assessment

Describe the worst-case impact if the vulnerability were exploited in production. Quantify the impact where possible — for example: "An attacker could drain up to $X million in SSV tokens from validator cluster balances." The impact assessment is the primary factor in determining severity and reward amount.

3. Proof of Concept

Include a fully reproducible PoC using Foundry or Hardhat. The PoC should run against a fork of mainnet or the Holesky testnet. Provide the exact commands needed to reproduce the exploit from a fresh environment.

forge test --match-test testExploit --fork-url $MAINNET_RPC -vvvv

4. Recommended Fix

Optionally include a recommended fix or mitigation. While not required, a well-researched remediation suggestion can increase the reward amount and demonstrates good faith from the researcher.

Protocol Architecture Overview

Understanding the SSV Network protocol architecture is essential for effective security research. SSV (Secret Shared Validator) technology splits a validator key into multiple key shares distributed across independent node operators. A threshold of operators must cooperate to sign each attestation, eliminating any single point of failure.

Core Components

  • Validators: Ethereum validators whose keys are split and managed by SSV operator clusters
  • Operators: Node operators who register on-chain and manage validator key shares
  • Clusters: Groups of 4+ operators assigned to manage a specific validator
  • DAO: Governance module controlling fee parameters and protocol upgrades
  • SSV Token: ERC-20 token used to pay operator fees and stake in the network
