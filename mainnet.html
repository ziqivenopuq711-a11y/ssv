Mainnet Assets & Scope

Live Ethereum Mainnet smart contracts in scope for the SSV Bug Bounty Program. Critical vulnerabilities affecting real user funds are eligible for rewards up to $250,000.

Mainnet Overview

The SSV Network Mainnet is the production deployment of the SSV protocol on Ethereum. All smart contracts listed here are live, hold real user funds, and are considered highest priority for security research. Vulnerabilities found in Mainnet contracts are eligible for the maximum reward tiers in the Bug Bounty Program.

SSV Network deployed its core contracts on Ethereum Mainnet to support decentralized validator operations at scale. The protocol manages operator registrations, validator cluster formation, and fee distribution. Each of these components represents a critical attack surface that researchers should carefully audit.

Reward Calculation: Mainnet asset vulnerabilities are calculated at 10% of funds at risk, up to a maximum of $250,000. The minimum reward for a Critical finding is $50,000, ensuring researchers are incentivized to report even smaller impact bugs.

Attack Surfaces & Research Areas

Security researchers should focus on the following high-impact areas when examining Mainnet contracts:

Fund Drainage & Reentrancy

Any path that allows an attacker to drain SSV tokens or ETH from cluster balances, operator earnings, or the DAO treasury. This includes classic reentrancy, cross-function reentrancy, and read-only reentrancy patterns.

Validator Slashing & Manipulation

Vulnerabilities that allow an attacker to cause legitimate validators to be slashed, manipulate validator cluster states, or force validators into an inactive state without authorization. This directly impacts stakers using the SSV protocol.

Governance & Access Control

Flaws in the DAO governance mechanism, fee update logic, or role-based access control that could allow an unauthorized party to change critical protocol parameters, drain fee revenue, or upgrade the protocol maliciously.

  • Unauthorized operator fee changes beyond DAO-enforced limits
  • Bypassing the onlyOwner or onlyDAO modifiers
  • Manipulation of the liquidation threshold to harm cluster operators
  • Storage collision or initialization issues in upgradeable proxies
  • Integer overflow/underflow in balance calculations
